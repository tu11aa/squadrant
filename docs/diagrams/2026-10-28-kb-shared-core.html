Phase 1 built the knowledge base for rules only. Phase 2a gives all four domains (rules, decisions, wiki, profile) one item model, one home rule, one merged read, one matcher, and one set of scores. Click through the three panels below.

1 · Where does a project's own knowledge live? (home resolution)

Pick a project config. The first rule that applies wins. Reads never create a KB; a pending home is created by the first write (phase 2b-2).

2 · What does a session read? (read set)

Hover a layer to see what it contributes. Shared layers: first one wins. The project home overrides a shared item with the same id; knowledge list still shows the hidden one as [acme/shared → overridden by projA]. Toggle the home to see a pending home drop out.

Hover a layer.
The folder decides the domain (D3)

…/rules/ = rule, …/decisions/ = decision. A rule's frontmatter domain: stays its category (coding, pr); in other domains it must equal the folder. CLI: --domain = KB domain, --category = rule category.

Reserved id prefixes (D4)

dec. decisions · wiki. wiki · prof. profile · rules keep <category>.<slug>. Ids are unique across domains, so the seen set, citations and scores key on the bare id. knowledge doctor checks both rules.

3 · Is each item useful? (audit lines → scores)

The audit log is append-only and never rewritten. Older lines are normalized when read. Step through one legacy line of each kind.
