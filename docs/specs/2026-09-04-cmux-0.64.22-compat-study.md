## 0. Headline

**The upgrade is low-risk and fixes a squadrant bug we currently work around.**

The single most consequential change is that cmux's Claude launch-argv sanitizer
(`AgentLaunchSanitizerPrimaryPolicies.claudePolicy` + `AgentLaunchPositionalScanning`) gained
`scansOptionsPastPositionals: true` in #8070. That is the exact mechanism behind **#697/#699 —
`launchCommand.arguments` truncated at `--messaging-socket-path`** — and it is repaired at 0.64.22.
No squadrant surface breaks. Two behaviours change in ways that are neutral-to-positive, one
(the socket event-stream generation revocation, #7988) needs a post-upgrade smoke test.

## 2. The `--messaging-socket-path` truncation, resolved at source

This is the finding worth the study. Prior work (#697/#699/#700, and the note at `launch-cmd.ts:87-90`)
established *empirically* that cmux truncates `launchCommand.arguments` at `--messaging-socket-path`,
and worked around it by moving the flag to the end of the launch command. The mechanism is now nailed down.

**Where the store argv comes from.** `agentLaunchCommandFromEnvironment` (CLI/cmux.swift) writes
`arguments: sanitizedArguments` — i.e. the store argv is **sanitizer output**, not raw argv.
The sanitizer is `AgentLaunchSanitizer.preserveOptions(_:policy:)` with `claudePolicy`.

**`--messaging-socket-path` is unknown to cmux.** It appears in neither `valueOptions`,
`optionalValueOptions`, `booleanOptions`, nor `variadicOptions` at **either** tag **[S]**.

**0.64.17 — truncation:**

```
optionWidth(): guard policy.valueOptions.contains(arg), index+1 < args.count else { return 1 }
  → "--messaging-socket-path" is not in valueOptions → width = 1 → flag kept, value not consumed
next iteration: args[i] = "/Users/…/x.sock" → !hasPrefix("-") → positional branch
  claudePolicy has no resumeSubcommand, preserveFirstPositional = false,
  and the path is not a nonRestorableCommand → falls through to `break`
```

Everything from the socket path onward is dropped. This is exactly the on-disk shape **[V]**:

```
["…/claude","-n","squadrant-captain-squadrant","--permission-mode","auto","--model","fable",
 "--effort","low","--append-system-prompt-file","…/captain.claude.md",
 "--plugin-dir","…/plugin","--messaging-socket-path"]     ← ends here, value gone
```

**0.64.22 — fixed:** #8070 added `scansOptionsPastPositionals: true` to `claudePolicy`, and
`consumePositional` gained a branch for it:

```swift
if policy.scansOptionsPastPositionals {
    if !policy.promptBoundaryOptions.isEmpty, sawOptionBeforePositional { return true }   // claudePolicy: empty → skipped
    if !sawPositional, policy.nonRestorableCommands.contains(arg) { return false }
    sawPositional = true; index += 1; return true        // ← index ADVANCES, loop continues
}
```

The socket path is consumed as a positional and scanning **continues** instead of breaking.
Separately, the new `unknownOptionWidth` returns **2** for an unknown flag whose value is followed
by another flag — so in the crew ordering (`claude.ts:59-69`, where `--plugin-dir` follows
`--messaging-socket-path`), both the flag **and** its value are preserved.

**Consequences for squadrant:**

1. `roleFromTemplate` (`store-fingerprint.ts:68-75`) will classify from the store argv directly,
   without falling back to `ps`. The `argvCache` / `readArgvFromPid` path (`:37-63`) becomes a
   rarely-hit safety net rather than the load-bearing path for captains.
2. The `#697` ordering constraint in `launch-cmd.ts:87-93` becomes unnecessary at 0.64.19+.
   **Keep it anyway** — it is harmless on both versions and is the only thing that makes a
   downgrade or a mixed-version machine safe. Retire it only when `compatManifest.tools.cmux.min`
   is raised to `0.64.19`.
3. `claude.ts:59-69` (the crew path) currently emits `--messaging-socket-path` **before**
   `--plugin-dir`, contrary to the comment at `launch-cmd.ts:87` claiming it matches. On 0.64.17
   that means a crew's `--plugin-dir` is silently dropped from the store record (role classification
   still survives, because `--append-system-prompt-file` precedes the socket flag at `claude.ts:51`).
   On 0.64.22 both survive. **This is a pre-existing inconsistency worth its own issue**, independent
   of the upgrade.

## 3. What to bump in `packages/shared/src/lib/compat-manifest.ts`

```diff
- cmux:     { min: "0.64.0",  lastVerified: "0.64.17" } satisfies ToolEntry,
+ cmux:     { min: "0.64.0",  lastVerified: "0.64.22" } satisfies ToolEntry,
```

- **Bump `lastVerified` only after** the §1 verification column passes (rows 1, 4, 5, 9, 15, 17 are
  the ones that actually need a live run). `checkToolCompat` (`tool-compat.ts:32-38`) fires a
  stderr warning on *every* `probe()` while the installed version exceeds `lastVerified`, so leaving
  it stale is noisy, not safe.
- **Do not raise `min`** in this change. `0.64.0` remains the true floor for the CLI surface squadrant
  uses. A separate, deliberate bump to `0.64.19` would be the precondition for deleting the #697
  workaround and the `ps` argv-recovery fallback — that is a follow-up decision, not part of the upgrade.
- No other manifest entries move: `claude`, `node`, `codex`, `gemini`, `opencode` are untouched by this window.

**Nothing else needs to change.** `packages/shared/src/lib/__tests__/tool-compat.test.ts` mentions
`0.64.17` at lines 6-87, but every case passes an **inline** `{ min, lastVerified }` object rather than
importing `compatManifest` — the manifest bump does not touch the test suite. The `0.64.16` reference in
`packages/cli/src/commands/__tests__/launch.test.ts:323` is a prose comment, not a version pin.
`packages/shared/src/config.ts:165` documents an inert `agent-hibernation` note — worth re-reading against
0.64.22 but not blocking.

## 5. Recommended upgrade order

1. **Snapshot first:** `cp ~/.claude/settings.json /tmp/settings.pre` and
   `cp ~/.cmuxterm/claude-hook-sessions.json /tmp/store.pre`, and record
   `jq '.sessions | length' /tmp/store.pre`.
2. **Install manually via DMG**, not the in-app updater — this build ships the known-broken
   Sparkle 2.8.1 / SDK-15.5 combination (see the 2026-07-24 doc, §0). cmux issue #1984 means the
   update itself kills terminal sessions, so **close crews first** and expect captains to need relaunch.
3. **Bounce the daemon** (`launchctl kickstart -k gui/$(id -u)/com.squadrant.daemon`) so
   `installClaudeHooks` reconciles against whatever cmux wrote.
4. **Run the verification column** for rows 1, 4, 5, 9, 15, 17.
5. **Then** bump `lastVerified` to `0.64.22` and refresh the §4 docs.
6. **Only after that**, consider the two follow-up issues this study surfaces:
   - retire the #697 flag-ordering workaround + `ps` argv recovery (needs `min: 0.64.19`);
   - authenticate pid generation with `pidStartSeconds`/`pidStartMicroseconds` instead of bare
     `process.kill(pid, 0)` in `store-fingerprint.ts:112`.
   - fix the `--messaging-socket-path` / `--plugin-dir` ordering inconsistency in
     `packages/agents/src/drivers/claude.ts:59-69` (pre-existing, not upgrade-caused).

## 6. Method / reproducibility

Everything marked **[S]** was read from cmux source at the two tags without cloning the repo
(it is ~1.6 GB) and without upgrading anything:

```bash
# full blob trees at both tags, diffed by sha
for t in v0.64.17 v0.64.22; do
  gh api "repos/manaflow-ai/cmux/git/trees/$t?recursive=1" \
    --jq '.tree[] | select(.type=="blob") | .path + " " + .sha' > tree-$t.txt
done

# CLI/cmux.swift is 1.6 MB — the contents API will not inline it; use the blob API
```

## 7. Capabilities this window opens for squadrant

Two of the five are **not gated on the upgrade at all** — cmux 0.64.22's source is merely the
*evidence* that a structured signal exists. Ranked by value.

### C1. 🔴 `notification_type` replaces English substring matching — **no cmux upgrade needed**

`packages/agents/src/interactive/claude.ts:65-69` decides "is this crew blocked on a permission?"
by lowercasing `payload.message` and testing `includes("permission") || includes("approve")`.
That is the same fragility class as #499 (glyph drift): wording- and locale-dependent.

cmux 0.64.22 reads a **structured field** instead **[S]** (`CLI/cmux.swift` ~25070):

```swift
let notificationType = parsedInput.rawObject.flatMap { firstString(in: $0, keys: ["notification_type"]) }
switch notificationType {
case "permission_prompt": notifyCategory = .needsPermission; notifyPending = false
case "idle_prompt":       notifyCategory = .idleReminder;    notifyPending = (…hadPendingBackgroundWorkAtStop == true)
default:                  /* fall back to the cue classifier for older clients */
}
```

**[V] Verified on this machine, not inferred:** the installed `claude 2.1.260` binary contains
`notification_type` (6×), `permission_prompt` (15×), `idle_prompt` (3×). It is a **Claude Code hook
payload field**, not a cmux field — squadrant's own `squadrant hooks claude notification` receives it
on stdin today.

**[V] Important corollary:** the `agent.hook.*` frames on the `cmux events` stream are **redacted** —
a live `agent.hook.Notification` frame carries only `_source`, `_ppid`, `cwd`, `hook_event_name`,
`session_id`, `tool_name`, `workspace_id`. **No `message`, no `notification_type`.** So this signal
can *only* come from squadrant's own hook, which is why the upgrade is irrelevant to it.

**Proposed:** `isPermissionNotification` becomes `notification_type === "permission_prompt"`, with the
current substring test kept as the fallback for `notification_type == null`. Same shape as cmux's own
`default:` branch.

### C2. 🔴 `background_tasks` / `session_crons` — the real fix for #492 — **no cmux upgrade needed**

cmux's `hasActiveClaudeBackgroundWork` **[S]** (`CLI/cmux.swift` ~27856):

```swift
if let crons = obj["session_crons"] as? [Any], !crons.isEmpty { return true }
if let tasks = obj["background_tasks"] as? [[String: Any]] {
    return tasks.contains { ($0["status"] as? String) == "running" }
}
```

…and it gates on the result: `suppressNeedsInputState = (notifyCategory == .idleReminder && notifyPending)`.
An idle nag fired while background work is still running is **not** a "waiting for input" state.

That is precisely the #492 class (`project_2026_07_01_492_idle_flood.md`): three sources asserting
turn-end from pane-idle during a no-output tool call. squadrant already vetoes on `pendingTool` at the
`turn.completed` transition; `background_tasks` is a **second, structural** veto that also covers
Claude's own background tasks and session crons, which `pendingTool` cannot see.

**[V]** `background_tasks` (24×) and `session_crons` (3×) present in `claude 2.1.260`. cmux's own comment
pins the floor at **claude ≥ 2.1.145**; `compatManifest.tools.claude.min` is `2.1.32`, so guard on
absence (both cmux and squadrant must treat missing keys as `false`).

### C4. 🟡 `cmux workspace status` — a pre-inferred crew lane — **needs the upgrade**

New at 0.64.22 **[S]** (`case "status": runWorkspaceStatusCommand`, `CLI/cmux.swift:8553`).
Per `docs/cli-contract.md@v0.64.22:103`: `workspace status` prints the workspace's lifecycle status as
**effective / inferred / override**, with lanes `todo | working | needs-attention | review | done | auto`.
cmux **infers** the lane from agent activity on its own.

That maps close to 1:1 onto squadrant's crew states (`working` / `blocked` / `review` / `done`) and is an
**independent** source — useful as a cross-check for the watchdog, in the same spirit as the
"verify with ps/git before acting on any crew signal" rule.

**Read-only.** `docs/cli-contract.md@v0.64.22:482-488` states the checklist and manual status pins belong
to the user and agents must not `set`/`cycle` them unless asked. Consume `workspace status`; do not write it.

## 8. Live verification (2026-09-04)

Method: an **isolated** probe — `/tmp/cc-hook-probe/settings.json` registering dump-to-file hooks for
7 events, run via `claude --settings … --setting-sources project` (so the squadrant-managed
`~/.claude/settings.json` was not the source), first headless then in a throwaway cmux workspace
(`workspace:9`, cwd `/private/tmp/cc-hook-probe` — deliberately not a registered project, so
`projectFromCwd` never matches and the daemon ignores it). Workspace closed and orphan-checked
afterwards; workspace list returned to its original 5 and `ps` showed no surviving probe process.

### 8.1 The `notification_type` schema is a hard contract, not an optional extra

Extracted from the `claude 2.1.260` binary's own zod schema **[V]**:

```js
hook_event_name: k("Notification"), message: s(), title: s().optional(), notification_type: s()
```

`title` is `.optional()`; **`message` and `notification_type` are not**. cmux's `default:` fallback
branch exists for *older* Claude clients, not for a field that can go missing on a current one.

Full enum (`Xor` in the binary) — 14 values **[V]**:

```
permission_prompt        idle_prompt              auth_success
elicitation_dialog       agent_needs_input        agent_completed
elicitation_url_dialog   worker_permission_prompt push_notification
computer_use_enter       computer_use_exit        quota_auto_resume_fired
quota_auto_resume_stale  quota_auto_resume_disabled
```

plus `elicitation_complete` / `elicitation_response` accepted as matcher values.

**The finding that changes the design:** the binary's hook catalog declares

```js
Notification: { …, matcherMetadata: { fieldToMatch: "notification_type", values: [...Xor, …] } }
```

So a `Notification` hook is **matcher-scopable on `notification_type`**, exactly the way squadrant
already scopes `PreToolUse` to `AskUserQuestion` (#560). That removes string matching entirely:

| matcher | maps to |
|---|---|
| `permission_prompt`, `worker_permission_prompt` | `task.blocked` (awaiting permission) |
| `agent_needs_input` | `task.input.requested` |
| `idle_prompt` | `task.progress` (liveness only — and only when `background_tasks` is empty) |
| `quota_auto_resume_*` | quota/rate-limit state — squadrant has **no** source for this today |

Note in fairness: squadrant's current `isPermissionNotification` **does** match the real message
(`"Claude needs your permission"` contains `permission`). It is fragile, not broken — the case for
changing it is robustness, not a live bug.

### 8.2 `PermissionRequest` fires ~6 s before the Notification, with structure

Real captured payloads **[V]** (probe session, Write tool in `default` permission mode):

```jsonc
// PermissionRequest — t+0.000s
{ "hook_event_name": "PermissionRequest", "tool_name": "Write",
  "tool_input": { "file_path": "…/needs-approval.txt", "content": "HELLO" },
  "permission_suggestions": [ { "type": "setMode", "mode": "acceptEdits", "destination": "session" } ],
  "prompt_id": "204d13c6-…", "permission_mode": "default",
  "session_id": "2be9e9d8-…", "cwd": "/private/tmp/cc-hook-probe", "scratchpad_dir": "…" }

// Notification — t+6.007s
{ "hook_event_name": "Notification", "message": "Claude needs your permission",
  "notification_type": "permission_prompt", "prompt_id": "204d13c6-…", "session_id": "2be9e9d8-…" }
```

`PermissionRequest` is strictly better as a blocked signal: **6 seconds earlier**, and it names the
tool and its input, so `task.blocked.question` can say *what* is being asked instead of the generic
"Claude needs your permission". `permission_suggestions` even carries the escalation cmux would offer.

### 8.3 `background_tasks` / `session_crons` are real, and `Stop` carries two more useful fields

Real captured `Stop` payload **[V]**:

```jsonc
{ "hook_event_name": "Stop", "session_id": "4cdffe9d-…", "transcript_path": "…",
  "cwd": "/private/tmp/cc-hook-probe",
  "prompt_id": "6a4c4ca8-4b96-419b-b0f9-9b6f167fc1ba",
  "permission_mode": "default",
  "stop_hook_active": false,
  "last_assistant_message": "PROBE_OK",
  "background_tasks": [],
  "session_crons": [] }
```

Both fields present (empty here, as expected for a trivial turn). Schema-wise they are `.optional()`,
so absence must still be treated as `false` — matching cmux's handling.

**Two unplanned finds in the same payload:**

- **`prompt_id`** — a real per-turn identifier, present on `Stop`, `PermissionRequest` and
  `Notification` (and it *matched* across the PermissionRequest/Notification pair above, so it
  correlates them). `packages/agents/src/interactive/claude.ts` currently emits
  `{ type: "task.turn.completed", turnId: "hook-stop" }` — a **constant**. A real turn id is exactly
  what the #492 turn-boundary work needed and could not get.
- **`permission_mode`** on `Stop` — the same field cmux #8070 persists as `lastPermissionMode`.
  squadrant could observe a crew that silently switched into `acceptEdits`/bypass mid-session.
